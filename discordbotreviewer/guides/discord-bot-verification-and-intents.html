Discord Bot Verification and Intents Explained: What Developers Need to Know

Understand Discord app verification, privileged Gateway intents, OAuth2 installation, permissions and the current review thresholds.

DISCORD BOT REVIEWER EDITORIAL9 NOVEMBER 202610 MIN READ
d.
DISCORD BOT REVIEWER · DEVELOPER GUIDE

“Verification” is confusing because developers use it to describe several different Discord processes. App verification, privileged-intent access and App Directory Discovery are related, but they are not the same. Knowing the difference helps you prepare the right information and avoid requesting access your bot does not need.

1. Start with the application

Every Discord bot belongs to an application in the Developer Portal. The application holds its identity, bot user, OAuth2 configuration and other settings. Keep its name, icon, description, support links and developer contact information accurate. These details help server owners understand who operates the app.

2. What app verification means

App Verification is an application-level review. It is relevant to developers who want access to certain platform capabilities, including enabling Discovery and monetization. The exact qualification requirements and evidence are shown in the app's Verification section in the Developer Portal and can change over time.

Prepare a clear explanation of what the bot does, who operates it, how users get support, what permissions it needs and how it handles data. Make sure the app works and its public description matches its actual behavior. Do not describe planned features as shipped.

3. Gateway intents control the events you receive

Intents are flags sent when your bot identifies to Discord's Gateway. They tell Discord which event groups your app wants. Without an intent, you will not receive its associated Gateway events. Standard intents are generally available; privileged intents require extra configuration.

The three privileged intents are Guild Members, Guild Presences and Message Content. Guild Members covers member join, leave and update events and member-list access. Guild Presences covers status and activity updates. Message Content controls access to user-authored message content fields, including message text and certain content-related data.

4. The current privileged-intent review threshold

Discord's June 2026 documentation describes the review threshold in terms of 10,000 unique users who can see the app across the servers where it is installed, rather than the older 100-server threshold repeated in many tutorials. An app in a few large communities can reach the user threshold, while an app in many small communities may not.

Below the threshold, developers can enable the privileged intents they genuinely need in the Developer Portal. Once the app reaches the review threshold, Discord may require an application for continued access. The Developer Portal will show the relevant notice and process. Check current official docs before relying on older videos.

5. Enable an intent in both places

For a privileged intent, the Developer Portal setting and your code must agree. Enable the required intent under Bot settings, then request it in your library's Gateway configuration. If your code requests an intent that is not enabled or approved, the Gateway can close the connection with a disallowed-intents error.

Do not enable all privileged intents “just in case.” Request only what your features require. If a slash command, button or context menu can perform the task without broad message access, consider that alternative.

6. Explain your use case clearly

A strong review explanation connects a specific feature to the data access it needs. “We need Message Content for moderation” is vague. Explain which messages the moderation feature checks, what risks it detects, why interaction alternatives are insufficient, what happens to the content and how long records are retained.

For Guild Members, explain the exact member events or list access required. A welcome bot may need join events to greet members; a role synchronization feature may need member updates. For Presences, explain why online status or activity changes are essential. If the bot works without presence data, do not request it.

Be transparent about storage, sharing, retention, deletion and security. Screenshots or short videos can demonstrate the feature in context. Be specific and truthful; do not claim data is discarded if it is stored.

7. App Directory Discovery is separate

Verification does not guarantee that an app will be widely discovered. Discovery has its own eligibility and product-page requirements. Developers should provide a concise description, relevant tags, accurate support links and a useful product page. Read the official Enabling Discovery guide for current steps.

8. Installation permissions still matter

OAuth2 scopes and bot permissions determine how an app is installed and what it can do in a server. Request only permissions needed by selected features. Use channel-specific permissions where possible and explain why access is required. A verified application is not automatically safe to grant Administrator.

Developer checklist

  • Keep the application identity and description accurate.
  • List every feature that depends on a privileged intent.
  • Try interactions and alternatives before requesting message or member data.
  • Enable the intent in the portal and request it in code.
  • Prepare concrete examples and truthful data-retention details.
  • Review current thresholds and reapplication requirements.
  • Use least-privilege OAuth2 permissions and provide support information.

Platform rules change. Use Discord's Gateway Intents documentation and Privileged Intent Review guide as the source of truth.
